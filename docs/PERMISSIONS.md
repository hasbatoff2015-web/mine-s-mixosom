# Права игрока и оператор

Ник — это подпись над головой. Его выбирает клиент. Он не доказывает, кто это.

Сервер при первом входе выдаёт `playerId`. Это UUID. Пока у игрока живой игровой `sessionToken`, повторный вход возвращает тот же `playerId`. Права висят на этом id.

Смена ника права не переносит. Другой игрок с тем же ником, в любом регистре, чужие права не получает.

Это не защита от кражи игрового `sessionToken`. Если токен сессии утёк, вошедший получает тот же `playerId`. Отдельных аккаунтов здесь нет.

## Как узнать playerId

В журнале сервера строка входа выглядит так:

```text
player joined: Misha (961c35e9-9b9f-4a01-b3a0-ee96fa352a60)
```

Скобки — это `playerId`.

Пока игрок в мире, оператор может посмотреть id:

```text
/permissions info Misha
```

Если такой ник один, ответ содержит строку `Id:`. Если ников несколько, команда откажется и попросит id. Сама команда `info` права не выдаёт.

## Выдать и снять OP

Оператор или консоль:

```text
/op 961c35e9-9b9f-4a01-b3a0-ee96fa352a60
/deop 961c35e9-9b9f-4a01-b3a0-ee96fa352a60
```

Можно написать ник, только если ему соответствует ровно один онлайн- или сохранённый игрок. Сервер записывает его `playerId`, не ник.

Неизвестный ник не создаёт запись. Два игрока с одним ником — команда отклоняется, никто новый права не получает.

Роль и отдельное право — так же, только на найденный id:

```text
/permissions role assign Misha vip
/permissions grant Misha holograms.create
```

Обычный игрок эти команды не выполняет.

## Список операторов в env

`FC_OPERATORS` и `OPERATORS` принимают только `playerId`, через запятую:

```bash
FC_OPERATORS=961c35e9-9b9f-4a01-b3a0-ee96fa352a60
```

Ник в этом списке ничего не даёт. В журнале будет строка, что ник проигнорирован. Игрок с таким ником оператором не станет. Записи сами на текущего игрока не переносятся.

Старый файл, где в `FC_OPERATORS` был ник, нужно поправить вручную: узнать `playerId` и подставить его. Пока там ник, этот человек оператором из env не является. Выдать право заново можно командой `/op` по id.

## Старый permissions.json

Раньше операторы, роли и отдельные права могли лежать под ником. При загрузке такие ключи уходят в поле `legacy` и перестают работать. Определения ролей (`default`, `admin`, `vip` и свои) не стираются. Записи с нормальным `playerId` остаются в силе.

Рестарт не включает старый ник обратно.

Пока запись в `legacy`, её видно в `/permissions info` как `Legacy nickname entry: inactive`. Это не выдача права.

Перенос делает только явная команда с подтверждённым id:

```text
/permissions migrate LegacyOp 961c35e9-9b9f-4a01-b3a0-ee96fa352a60
```

Второй аргумент — именно id, не ник. Если передать ник, команда отклоняется, даже когда игрок с таким ником один. Так чужой человек не забирает старую запись только потому, что назвался так же.

После переноса права есть только у этого id. Повторный запуск ту же legacy-запись уже не находит.

Неизвестный ник, пустой id и неоднозначная цель отклоняются. Новая запись под ником не создаётся.

## Обычные игроки

Роль `default` по-прежнему есть у всех: `/spawn`, дом, `/tpa`, `/rtp`, `/back`, баланс, `/pay`, аукцион, обмен, скупщик, друзья, обычный приват. Она не смотрит на ник.

Роли `vip` и `premium`, выданные на `playerId`, остаются у этого id после смены ника, выхода и рестарта.

## Это не вход в закрытую админку

`FC_ADMIN_IDS` и токены из `docs/ADMIN.md` — два администратора приватного HTTP. `/op` их не открывает. Игровой `sessionToken` туда не входит. Ник, похожий на id администратора, не делает игрока ни оператором, ни администратором панели.

Вернуть законному игроку старое право: найти его текущий `playerId` в журнале входа или в `/permissions info`, затем `/permissions migrate` или новый `/op` по этому id.

## Приваты

Новый приват записывает владельца как `playerId` того, кто его создал. Участники — тоже `playerId`. Ник, даже с другим регистром, владельцем и доверенным не считается.

`/claim addmember` принимает ник только если он указывает ровно на одного известного игрока. Тогда в список попадает его id. Несколько игроков с одним ником — команда отклоняется, имя в список не пишется.

Старый приват, где владелец или участник записан ником, на диске остаётся. Он по-прежнему закрыт: чужой игрок с тем же ником не ломает, не ставит блоки, не удаляет и не меняет флаги. Сам старый ник права не включает. Пока запись не перенесена, её не открывает и тот, кто сейчас так называется.

Перенос делает только консоль сервера, после того как владелец сам проверил, чей это id:

```text
claim migrate-owner <claimId> <playerId>
claim migrate-member <claimId> <старый-ник> <playerId>
```

Повтор той же команды не плодит участников и не меняет флаги и координаты. Если у привата уже есть владелец-id, другой id поверх не пишется.

Кланный приват `clan:<id>` и ивентовый `__world_events__` никами не являются. Их эта миграция не трогает. Доступ к базе клана по-прежнему через состав клана. Защита ивента остаётся.

## Дома

Новый дом записывается на `playerId`. Смена ника список не отдаёт другому. `/home`, `/sethome`, `/homes`, `/delhome` и меню домов читают только дома этого id.

Старые дома, лежавшие под ником, при загрузке уходят в `legacy`. Игрок с таким ником их не видит, не телепортируется и не удаляет. Консоль:

```text
home migrate <старый-ник> <playerId>
```

Если у игрока уже есть дом с тем же названием, перенос не затирает ни старый, ни новый список. Повтор после успешного переноса второй копии не создаёт.

## Оператор из окружения

`FC_OPERATORS` даёт OP только пока id записан в env. При старте эти id в `permissions.json` не копируются. Убрали id из env и перезапустили процесс — этот OP пропал.

`/op <playerId>` пишет отдельный ручной OP. Он остаётся после рестарта и после удаления env. Если id есть и в env, и выдан через `/op`, снятие из env ручной OP не стирает. `/deop` при живом env отвечает, что окружение всё ещё даёт OP, и не притворяется, что право снято.

Старый файл, где в `ops` уже смешаны ручные id и бывшие env-id, не разбирает источник сам. Такие id при первом запуске этой версии попадают в `unreviewedOps` и никого не делают оператором. Ник в этом списке по-прежнему не работает. Вернуть нужного человека: консоль и `/op` по его `playerId`. Перед правкой живого мира сохраните копию `plugin-data/permissions.json`, `plugin-data/claims/claims.json` и `plugin-data/home/homes.json`. Откат — вернуть эти файлы из копии и перезапустить процесс. На боевой VPS этот проход ничего не применяет.
