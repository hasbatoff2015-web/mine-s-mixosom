# Повтор покупки у продавца вне истории JSON

## Goal

На ветке интеграции PR #141 повтор JSON-покупки узнавался по `pairId` в `economy/transactions`. Видимая история — 100 строк, а сам массив обрезается после 20 000 записей до 10 000. После выпадения pair id тот же `clientRequestId` списывал деньги ещё раз. Production-шаблоны не задают `FC_ECONOMY_BACKEND`, поэтому процесс остаётся на `legacy_json`.

## Result

Завершённая покупка с UUID хранится в `settledPurchases` файла скупщика. Повтор того же id не списывает деньги и не выдаёт второй стак ни после 101 посторонней транзакции, ни после перезапуска, в котором pair id уже удалён из журнала. Другой игрок, предмет, количество или сумма с тем же UUID получают отказ без списания. Postgres-источник `TRADER_PURCHASE` сохранён: оплаченный резерв выдаётся один раз, неоплаченный удаляется без предмета.

## Implemented

- `BuyerService` пишет settled-запись в том же `persist()`, что и выдачу.
- Загрузка читает её до `recoverPurchases`. Восстановление оплаченного резерва тоже отмечает запрос.
- Запись не обрезается вместе с журналом экономики.

## Architecture decisions

Защита повтора не может жить в скользящем журнале. `settledPurchases` — отдельный список только для UUID покупки продавца. Покупка без UUID по-прежнему получает новый `sp-` id: честный клиент и так шлёт новый UUID на каждое нажатие.
