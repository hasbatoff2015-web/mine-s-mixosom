# Автоматический Яндекс ID, гость и закрытие hardening

Дата: 2026-11-04

## Goal

Убрать ручную кнопку «Привязать Яндекс ID». Если игрок уже авторизован в Яндексе, подключение само открывает его персонажа или привязывает текущего гостя. Если не авторизован, он играет гостем браузера. Одновременно закрыть гонку слота при переподключении и перенести в git два ручных исправления `scripts/fc-backup.sh`.

## Result

Клиент и сервер реализуют этот сценарий. Кнопки привязки в паузе нет. Сервер по-прежнему доверяет только HMAC подписанного `uniqueID`. `isAuthorized()` остаётся подсказкой клиента. Живой PostgreSQL и черновик Яндекс Игр в этой среде не запускались. VPS не менялся.

Статус: IMPLEMENTED, LIVE QA REQUIRED.

## Implemented

- Молчаливая проверка `isAuthorized()` при «Подключиться». Диалог SDK открывается только из «Войти через Яндекс» и только если игрок ещё не авторизован.
- `join.authMode = yandex_auto`. Сервер ищет связь. Есть UUID — открывает его. Нет связи — гостевой вход и идемпотентная привязка до welcome. Конфликт локального гостя не сливает персонажей.
- Welcome получает `yandexSync`: `linked`, `restored`, `unavailable` или `guest`. Текст «Прогресс сохранён…» показывается только после `linked`.
- При обрыве старой сессии во время переподключения один слот остаётся за этим UUID. Чужой `connectionId` не отключается.
- `read_env_value` снимает CR. Проверка манифеста не использует `grep -q`.

## Architecture decisions

Один сервис SDK и один сервер. Отдельной учётной записи нет.

Клиент не считает подписанный профиль гостя Яндекс Игр переносимым аккаунтом. На сервер профиль уходит только когда `isAuthorized()` истинно. Сервер всё равно не читает этот boolean: пакет с `isAuthorized: true` и без годной подписи связь не создаёт.

Если в браузере уже есть гостевой ключ того же UUID, повторный вход не тратит proof. Тот же proof без ключа после потребления не создаёт второго игрока. Новый браузер присылает новую подпись и получает прежний UUID.

Файл мира и PostgreSQL не одна транзакция. Если связь записана, а welcome не дошёл, UUID остаётся и следующая годная подпись его открывает. Если база недоступна, гость играет дальше, а клиент не говорит, что прогресс привязан. Ровно одной доставки между базой и браузером нет.

`FC_YANDEX_AUTH_ENABLED` остаётся выключателем. Survival и Peaceful при выключенном флаге не получают фиктивный успех. Новый флаг не добавлялся: старый клиент не понимает `yandex_auto` и просто входит гостем, новый клиент на старом сервере тоже остаётся гостем, потому что неизвестный `authMode` отбрасывается.

## Root causes

Кнопка привязки существовала, потому что сервер связывал `uniqueID` только по отдельному `auth_link` после уже открытой гостевой сессии. «Войти через Яндекс» умел только `resume_yandex` и при отсутствии строки отвечал «войдите гостем и привяжите».

Гонка слота: `holdJoinSlot` для уже подключённого UUID не держал `pendingJoinSlots`. После `await` старый сокет мог отключиться, `onlineCount` падал, и чужой вход занимал место до публикации переподключения.

CRLF: `read_env_value` оставлял `\r`, и порт не проходил числовую проверку. `grep -q` в конвейере с `pipefail` закрывал `tar` по SIGPIPE, хотя `manifest.json` в архиве был.

## Performance

На игровой тик новых вызовов SDK и SQL нет. Одно подключение авторизованного игрока — один `getPlayer`, если результат этой загрузки ещё не закэширован, одна проверка HMAC и один lookup. Привязка добавляет bind и одну бронь proof. Повтор в том же браузере с тем же гостевым ключом lookup делает, но proof не тратит. Лимит SDK 20/5 мин сохранён.

## Known issues

Настоящий SDK, смена аккаунта на устройстве и PostgreSQL production не проверялись. Если consume после уже записанной связи бросает исключение, связь остаётся, welcome уходит, а бронь может остаться до истечения окна. Это закрывает повтор, но не обещает ровно одну доставку.

Гостевой `sessionToken` по-прежнему предъявительский. Игра не даёт гостю кнопку переноса на другое устройство, пока он сам не войдёт через Яндекс.

## Follow-up перед merge

«Остаться гостем» больше не возвращает в список, чтобы следующее «Подключиться» снова послало `yandex_auto`. Сразу выполняется гостевой вход A. Выбор помнится до конца загрузки страницы, снимается явным открытием персонажа Яндекса или сменой аккаунта и не пишется в `localStorage`.

`rollbackCandidate` не удаляет игрока, чья связь уже записана или чей исход записи неизвестен. Отказ публикации после bind не шлёт welcome и не стирает UUID. Повторный вход и загрузка мира заново открывают его.

Кэш proof живёт 8 минут, внутри серверного окна 10 минут. Та же подпись от SDK после этого окна не уходит на сервер повторно и диалог не открывается. Игрок видит просьбу перезагрузить игру.

До welcome подпись SDK описывается как «Вы авторизованы в Яндексе». Привязка прогресса называется только после `yandexSync` `linked` или `restored`.

Повторный прогон `npm run test:server` после этих правок завершился с кодом 0. Живой PostgreSQL по-прежнему NOT RUN.

## Follow-up 2

Конкурентная запись чужого UUID больше не открывает его сама, если в запросе был гостевой ключ. Неизвестный ключ тоже не становится разрешением войти чужим персонажем. Два первых входа без ключа по-прежнему оставляют одну связь.

`yandex_auto` с негодной или просроченной подписью и без известного гостя не вызывает `join` и не создаёт UUID. Известный гость при такой ошибке остаётся собой, welcome несёт `yandexSync: guest`. Первый вход при недоступной базе или выключенной авторизации тоже не создаёт персонажа, пока игрок отдельно не выберет обычный гостевой вход.
