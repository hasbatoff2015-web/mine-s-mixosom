# Реферальная программа

Программа работает на серверном UUID персонажа. Отдельных аккаунтов она не заводит. Гость может участвовать. Без привязки к Яндекс ID очистка браузера может оставить этот UUID недоступным: меню говорит об этом прямо и не требует авторизации.

Подписанный `uniqueID` Яндекса подтверждает личность провайдера через уже существующий verifier. Это не доказательство отдельного входа в аккаунт Яндекса, и программа так это не называет.

Награды и время считаются только на сервере. Клиент не передаёт часы, ранг и факт выдачи кита.

## Правила

1. Игрок делится кодом или ссылкой.
2. Друг принимает приглашение сам. Загрузка игры ничего не принимает.
3. После принятия другу открывается право на кит `referral_starter`.
4. Друг должен набрать 3 часа (10 800 секунд) активной игры после принятия. Время до принятия не засчитывается.
5. Три часа копятся между сессиями и переживают перезапуск сервера.
6. Один приглашённый UUID засчитывается одному пригласившему. Второй код его не переписывает.
7. Свой код использовать нельзя.
8. За 3 подтверждённых друга пригласивший один раз получает VIP на 7 календарных дней.
9. За 5 подтверждённых друзей он один раз получает PREMIUM на 7 календарных дней.
10. Шестой и дальнейшие друзья новых порогов не дают.
11. IP, устройство, VPN и fingerprint не проверяются. Второй аккаунт может быть рефералом, если на нём действительно играют.

Сейчас часы копятся только в режиме Anarchy. Survival и Peaceful данные не смешивают: у каждого режима свой `deploymentId`, `serverMode` и `worldId`. В меню написано, что активность засчитывается на Анархии.

Список режимов можно расширить переменной `FC_REFERRAL_ACTIVITY_MODES` (через запятую). По умолчанию там только `anarchy`. Сервис не зашит в имя режима: флаг вычисляется при старте.

## Код

Код создаёт сервер при первом открытии раздела «Приглашения». Повторный запрос и перезапуск возвращают тот же код. Ник на код не влияет.

- 8 символов из алфавита `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` (нет 0/O и 1/I).
- Генерация: `crypto.randomBytes`. Байт делится на 32 без остатка, смещения нет.
- Ввод без учёта регистра.
- В PostgreSQL два уникальных ключа: scope + UUID владельца и scope + код.
- Если два запроса создают код одновременно, победитель один. Конфликт кода повторяется не больше пяти раз.

Код публичный. По нему нельзя прочитать инвентарь, баланс или сессию.

## Ссылка Яндекс Игр

Формат payload: `ref_CODE`.

Существующий `YandexGamesService` один раз читает `environment.payload` и `environment.app.id`. Второй `YaGames.init()` не создаётся.

Публичная ссылка строится так:

1. `FC_YANDEX_GAME_URL`, если это `https://yandex.ru/games/app/{число}` или `https://yandex.com/games/app/{число}`. Чужие параметры, включая секреты, отбрасываются. Добавляется только `payload`.
2. Иначе `FC_YANDEX_GAME_ID` из цифр.
3. Если сервер URL не знает, а SDK на клиенте отдал `app.id`, ссылку собирает клиент.
4. Вне Яндекс Игр и без официального URL показывается только код. Ссылка `localhost` не выдумывается.

Пока игрок сам не нажмёт «Принять приглашение», сервер связь не создаёт. Смена персонажа не переносит приглашение сама: кнопка нужна снова. Код из payload убирается из поля только когда сервер уже показывает принятую связь этого персонажа. Ошибка базы, чужой неверный код и собственный код payload не стирают. Два одновременных принятия одного UUID дают одну связь: второй ответ — «Вы уже приняли приглашение», а не сообщение о падении базы.

## Активное время

Сервер смотрит на своё состояние, не на пакеты клиента.

Засчитывается:

- добыча, установка блока, крафт;
- удар по игроку или мобу, попадание снаряда;
- рост серверного прогресса добычи;
- перемещение, если за секунду игрок сам сместился хотя бы на 0.6 блока по горизонтали.

Не засчитывается:

- простой, ping, heartbeat и пустые input-пакеты;
- удержание клавиши без смещения;
- только поворот камеры;
- падение, отбрасывание и другой сдвиг без собственного управления;
- телепорт и скачок дальше 12 блоков за окно;
- время без соединения и время мёртвого персонажа.

Последнее осмысленное действие открывает окно 5 минут. Внутри окна идут обычные паузы: стройка, инвентарь, чтение чата. После 5 минут без нового действия часы останавливаются. Открытая вкладка сама по себе три часа не даёт.

Секунды берутся из серверных часов. Один UUID не получает больше секунд, чем реально прошло. Просадка TPS лишние секунды не добавляет. Старое соединение после смены вкладки время не копит.

В базу пишется не каждый тик. Накопление сбрасывается примерно раз в 30–45 секунд, при выходе, при достижении 10 800 секунд и при остановке сервера. SQL не выполняется внутри шага 20 TPS.

Если ответ базы неясен, те же секунды второй раз не прибавляются. В худшем случае теряется одно ещё не записанное окно, обычно до 45 секунд. Уже записанный прогресс и выданные награды не откатываются. Пока база недоступна, в памяти держится не больше 60 незаписанных секунд, награда по ним не выдаётся, игра продолжается. Меню говорит, что зачёт временно недоступен.

Если при входе приглашённого база не ответила, сервер повторяет загрузку связи с паузой 0,2 с, 0,4 с, 0,8 с и далее, не чаще чем раз в 8 секунд. Повтор один на UUID и текущее соединение. После ответа базы трекер создаётся только для связи `pending` и только с актуальным `connectionId`. Секунды простоя без трекера не дописываются. Выход и остановка сервера повторы отменяют. Открытие меню тоже пробует поднять трекер, если игрок всё ещё в сети.

## Подтверждение

Когда записанные секунды достигают 10 800, статус связи в той же транзакции становится `qualified`. Повторный вход эту связь второй раз не считает. Пригласивший может быть офлайн: награда всё равно записывается. Счётчик друзей считается по строкам `qualified`, а не по сообщению клиента.

## Кит `referral_starter`

Предметы в коде не заданы. Администратор в игре наполняет инвентарь и выполняет:

```text
/kit create referral_starter
```

Удаление и выдача другим игрокам по-прежнему:

```text
/kit delete referral_starter
/kit give <игрок> <название>
```

Реферальная выдача не идёт через чат-команду и не открывает `kit.admin`. Имя кита фиксировано.

Пока набора нет или он пустой, право остаётся в состоянии «Ожидает настройки». Пустой кит полученным не считается.

Если все предметы не помещаются, выдача не начинается. Нужно освободить место. Половина набора не выдаётся и на землю не падает.

Квитанция пишется в сохранение персонажа вместе с инвентарём (`players.json`, атомарная замена файла). Два запроса на один UUID ждут одну выдачу: второй не помечает набор полученным, пока первое сохранение не закончилось. Если запись мира не удалась, предметы и квитанция откатываются, а в PostgreSQL набор остаётся доступным. Если мир уже записан, а отметка в PostgreSQL нет, повтор видит квитанцию и предметы второй раз не создаёт.

В том же снимке персонажа лежит список отслеживаемых ресурсов этой выдачи. Resource Ledger учитывает их по ключу `referral:{id}` один раз и хранит эти ключи отдельно от обычного окна в 500 операций. Обычная добыча, крафт и `/give` по-прежнему вытесняют только свои ключи. Если файл учёта потерян, следующий запуск восстанавливает выдачу из снимка персонажа, а ещё один запуск её не удваивает.

## Ранги

`DonationRankService.grant()` по-прежнему заменяет оплаченную запись. Реферальная программа его для наград не вызывает.

Оплаченный ранг лежит в `plugin-data/donation/ranks.json`. Реферальные VIP и PREMIUM лежат в `referral_rewards`. Эффективный ранг — больший из действующего оплаченного и действующего реферального:

`default < VIP < PREMIUM < BOSS < TITAN`.

OP свои права не теряет и оператором из-за рефералки не становится.

Примеры:

- Нет ранга, реферал VIP: эффективный VIP.
- Оплаченный VIP и реферальный VIP: оплаченная запись на месте, реферальный срок не стирается.
- Оплаченный VIP и реферальный PREMIUM: пока PREMIUM действует, эффективный ранг PREMIUM. Потом возвращается оплаченный VIP, если он ещё не истёк.
- Оплаченный TITAN и реферальный VIP: TITAN остаётся. VIP ждёт и не тратит календарные дни, пока его перекрывает более высокий ранг.
- Оплаченный BOSS и реферальный PREMIUM: BOSS не понижается.
- Оба порога сохраняются. PREMIUM не удаляет право на VIP. Пока PREMIUM впереди, остаток VIP стоит на паузе.

Срок реферальной награды календарный. Пока награда перекрыта, её остаток не идёт. Перезапуск длительность не увеличивает: у активной награды абсолютный `expires_at`.

Запись фаз VIP и PREMIUM сериализована по игроку. В таблице `referral_rewards` колонка `revision` (миграция `0012`) принимает только более новую ревизию. Опоздавший снимок не затирает уже записанный. Чтение из PostgreSQL тоже не подменяет более новую строку в памяти: сравнивается ревизия каждой награды, а незавершённая запись сохраняет локальную фазу и остаток. Новая строка из базы, которой в памяти ещё нет, добавляется.

Остановка сервера сначала дописывает активное время. Награда, которая появилась на этом последнем flush, сохраняется после него. Если эта запись не удалась, остановка завершается ошибкой и пишет её в лог сервера. При ошибке базы повтор читает текущую память, а не старый снимок.

`effectiveRank`, лимиты домов, приватов и аукциона, узлы прав и донатное меню читают этот эффективный ранг. SQL внутри этих вызовов нет: при входе и после транзакции награды в памяти лежит небольшой кэш, срок проверяется по серверным часам.

Если файл оплаченных рангов не прочитался, реферальная надбавка поверх него не включается, чтобы не показать VIP вместо нечитаемого TITAN. Сами строки наград в PostgreSQL не удаляются.

## База

Новая миграция `0011_referral_program`. Миграции `0001`–`0010` не менялись.

Таблицы:

- `referral_codes`
- `referral_relations` — одна связь на invitee в scope
- `referral_rewards` — одна строка на игрока и порог `3_confirmed` / `5_confirmed`
- `referral_kit_claims`

Отдельной таблицы событий активности нет. Секунды обновляются сравнением `active_seconds = ожидаемое значение`, поэтому повтор того же шага не удваивает прогресс.

Без `FC_DATABASE_URL` программа честно пишет, что нужна PostgreSQL. Игра при этом продолжается.

## Меню и протокол

Раздел: **Друзья → Приглашения**. Старые заявки, список, чат и телепорт друзей на месте.

`PROTOCOL_VERSION` не менялся. Добавлены действия `referral_refresh`, `referral_accept`, `referral_claim` и экран `friends-invites`. Старый клиент эти кнопки не рисует. Неизвестное действие сервер отвечает ошибкой и не падает.

Принятие и выдача ограничены по частоте. Обновление экрана не чаще одного раза в 2 секунды.

## Проверка в DEV

Часы вручную начисляет только оператор и только при `FC_REFERRAL_DEV=1`. В `npm run dev:server` и в production этот флаг выключен.

```text
/referral
/referral status <игрок>
/referral dev addtime <игрок> <секунды>
/referral dev qualify <игрок>
```

`qualify` дописывает до 10 800 секунд тем же серверным путём. Команда пишет строку в серверный лог и, если PostgreSQL включена, в `admin_audit_log`.

Локальные тесты:

```text
npm run typecheck:server
npm run typecheck:client
npm run check:boundaries
npx vitest run tests/server/referral.test.ts tests/server/referral-activity.test.ts tests/server/referral-world.test.ts tests/referral-menu.test.ts
FC_TEST_DATABASE_URL=postgresql://... npx vitest run tests/server/referral-postgres.integration.test.ts
```

`FC_TEST_DATABASE_URL` не должен указывать на production. Пароль в репозиторий не кладётся.

## Черновик Яндекс Игр

1. Задать `FC_YANDEX_GAME_URL` официальным адресом игры или положиться на `app.id` из SDK.
2. Открыть игру по `?payload=ref_КОД`.
3. Убедиться, что код подставился в поле, а связь появилась только после кнопки.
4. Повторить на телефоне в альбомной ориентации: раздел внутри «Друзья», длинный список прокручивается.
5. Запуск без SDK не должен ронять игру: остаётся код.

## Откат релиза

Миграция `0011` только создаёт таблицы. Откат кода их не удаляет и реферальные строки не стирает. Старый сервер эти таблицы не читает. Повторный запуск нового кода подхватывает те же связи, секунды и награды.

Не удалять таблицы, если нужно сохранить приглашения.

## Ограничения

- Эвристика движения не отличает человека от аккуратного бота. Это не античит.
- Незаписанное окно секунд при аварии процесса может потеряться.
- Живой SDK Яндекс Игр и production-база этой веткой не прогонялись.
- Survival и Peaceful часы не копят, пока их нет в `FC_REFERRAL_ACTIVITY_MODES`.
